# LocalMark 后端与存储接口草案

> 状态：草案，未实施。起草于 2026-10-09，基于插件 0.3.43 源码，以及 `D:/AI/meowa-outline` 网页参考库实验的核对结果。
> 本文中的类型名、路由和字段都是建议值，实施时以评审结论为准。

## 1. 目标与范围

### 目标

1. 插件可以在三种存储模式之间切换：
   - 仅浏览器；
   - 本地文件夹，即现有的 Markdown/JSON 落盘；
   - 服务器。
2. 服务器模式需要账号登录，按 workspace（个人库、团队库）隔离数据和权限。
3. 服务器地址可配置，可以登记多台服务器并在它们之间切换。不同服务器、不同 workspace 的本地缓存互不混用。
4. UI 层（content、侧栏、仪表盘、设置页）不再直接接触 IndexedDB 或目录句柄，只通过消息调用 background 中的 `LibraryRepository`。
5. 离线可用：断网时照常标注，联网后自动上传；冲突沿用现有的“保留本机 / 采用另一份”交互。

### 不在首版范围

- 分享链接、评论和团队成员管理界面。数据模型会预留，但不在首版实现。
- 服务端渲染网页全文，以及服务端生成 Markdown。
- 同一个 workspace 同时同步到本地文件夹和服务器两个目标。

这两种目标的冲突来源不同，首版只允许选一个；服务器模式下的本地文件夹只作为“导出”使用。

## 2. 分层

```text
content / sidepanel / dashboard / settings
        |  chrome.runtime 消息（保留现有 Request 类型，见 src/protocol.ts）
        v
background
  LibraryRepository   业务读写入口：校验、生成 op、写本地缓存、通知 changed
        |
  LocalCache          IndexedDB：按记录存储，加上 outbox、游标和冲突
        |
  SyncCoordinator     调度 pull/push、重试、冲突落盘（替代现有 scheduleSync）
        |
  SyncAdapter         接口，有三种实现：
    - NoneAdapter         只用浏览器缓存，不同步
    - LocalFolderAdapter  包装现有 SyncEngine 和 DirectoryFiles
    - RemoteAdapter       调用 HTTP API v1
        |
  AuthSession / MediaStore
```

### 与现状的对应关系

- **`src/db.ts`**：现在是单个 `kv` 存储，整个 Library 作为一个值。改为 `LocalCache` 中的多个 object store，详见第 4 节。
- **`src/files.ts` 的 `Files` 接口**：只在 `LocalFolderAdapter` 内部使用，不再是同步层对外的接口。
- **直接访问目录句柄的模块**：`settings.tsx`、`metadata-location.ts`、`metadata-export.ts`、`page-delete.ts`，以及 background 中处理图片的部分。这些访问全部收进 `LocalFolderAdapter` 和 `MediaStore`。
- **`expectedUpdatedAt`、`expectedMark`、`expectedTitle` 等乐观校验字段**：保留，用于本机多窗口之间的竞争；跨设备并发改由记录的 `version` 判断。

## 3. 领域记录

现有的 `Page` 把标注、视频标注都嵌在一个文档里。同步时改为拆成独立记录。这样可以减少冲突面：两台设备给同一个网页各加一条标注，不会互相冲突。

在本地文件夹模式下，`LocalFolderAdapter` 负责把拆开的记录重新聚合成现有的 `data/.../<title>--<id>.json` 和 `分类标签.json`，磁盘格式保持不变。

```ts
/** 所有可同步记录的公共元数据。 */
interface RecordMeta {
  /** 记录主键，在 workspace 内唯一。 */
  id: string;
  /** 服务端单调递增版本号；本地新建、尚未上传时为 0。 */
  version: number;
  createdAt: string;            // ISO 8601
  updatedAt: string;            // ISO 8601，客户端写入时间，仅用于展示和排序
  updatedBy?: string;           // 服务端填写的用户 ID；本地模式下不填
  /** 墓碑：删除后保留记录，供其他设备感知删除。 */
  deleted?: { at: string; by?: string };
}

type RecordKind = "page" | "mark" | "videoMark" | "taxon" | "workspaceSettings";

/** 网页。id 沿用现有规则：规范化 URL 的 SHA-256 前 16 位。 */
interface PageRecord extends RecordMeta {
  kind: "page";
  url: string;
  originalUrl: string;
  title: string;
  favicon: string;
  categoryId: string;           // 默认为 "category:uncategorized"
  tagIds: string[];
  comment?: string;
  rating?: 1 | 2 | 3 | 4 | 5;
  /** 本地落盘用的文件夹名和 Markdown 文件名，仅本地文件夹模式使用，服务端原样保存。 */
  local?: { folderName: string; markdownFile?: string };
}

/** 文字或元素标注，对应现有的 Mark。 */
interface MarkRecord extends RecordMeta {
  kind: "mark";
  pageId: string;
  text: string;
  note: string;
  color: Color;                 // 现有 ColorSchema
  anchor: MarkAnchor;           // 现有 AnchorSchema，原样保留
  tags: string[];               // 旧字段，只读兼容
  media?: MediaRef;             // 替代 imagePath
}

/** 视频标注，对应现有的 VideoMark。 */
interface VideoMarkRecord extends RecordMeta {
  kind: "videoMark";
  pageId: string;
  videoKind: "subtitle" | "keyframe" | "screenshot" | "comment";
  videoKey: string;
  time: number;
  trackId?: string;
  from?: VideoCueRef;
  to?: VideoCueRef;
  text: string;
  note: string;
  color: Color;
  media?: MediaRef;
}

/** 分类或标签，从现有 Taxonomy 文档拆成逐项记录。 */
interface TaxonRecord extends RecordMeta {
  kind: "taxon";
  taxonKind: "category" | "tag";
  name: string;                 // 在同一 workspace、同一 taxonKind 下唯一（服务端约束）
  description?: string;
  order?: number;
}

/** workspace 级共享设置。每个 workspace 一条，id 固定为 "settings"。 */
interface WorkspaceSettingsRecord extends RecordMeta {
  kind: "workspaceSettings";
  colorDescriptions?: Partial<Record<string, string>>;
}

/** 媒体引用。用内容哈希，不用路径；本地模式下由适配器映射成 media/<pageId>/<uuid>.png。 */
interface MediaRef {
  sha256: string;               // 64 位十六进制
  mime: "image/png" | "image/jpeg" | "image/webp";
  bytes: number;
  /** 本地文件夹中的旧路径，迁移和回写时使用。 */
  localPath?: string;
}

type SyncRecord =
  | PageRecord | MarkRecord | VideoMarkRecord | TaxonRecord | WorkspaceSettingsRecord;
```

### 设备级设置不参与同步

以下设置继续留在设备本地，存在 `chrome.storage.local` 或本地缓存的 `deviceSettings` 中，不进入服务器：

- `highlightPalette`
- `pageTools`
- `autoGenerateMarkdown`
- `lastColor`

### 关于 ID

- 页面 ID 由 URL 派生。同一个 URL 在不同 workspace 中会得到相同的 ID，所以服务端主键是 `(workspaceId, kind, id)`。
- 标注和分类继续使用客户端生成的 uuid。客户端离线时就能确定 ID，不需要服务端分配。
- 固定 ID `category:uncategorized`、`category:default:N` 保持不变。

## 4. 插件内部接口

### 4.1 存储配置（StorageProfile）

```ts
type StorageProfile =
  | { id: string; mode: "browser"; label: string }
  | { id: string; mode: "localFolder"; label: string; directoryName?: string }
  | {
      id: string;
      mode: "remote";
      label: string;
      server: ServerEndpoint;
      workspaceId?: string;       // 登录后选择
      account?: { userId: string; displayName: string; email?: string };
    };

interface ServerEndpoint {
  /** 只允许 https；开发时允许 http://localhost 和 http://127.0.0.1。 */
  baseUrl: string;              // 例如 https://localmark.example.com
  /** 首次连接时从 GET /v1/meta 读取，用于确认对方是 LocalMark 服务以及协议版本。 */
  serverId?: string;
  apiVersion?: string;
}

interface ProfileRegistry {
  list(): Promise<StorageProfile[]>;
  active(): Promise<StorageProfile>;
  /** 切换会停止当前同步、等待进行中的写入结束，然后加载目标配置对应的本地缓存。 */
  activate(profileId: string): Promise<void>;
  upsert(profile: StorageProfile): Promise<void>;
  /** 删除配置时会提醒用户：outbox 中尚未上传的操作会丢失。 */
  remove(profileId: string, options: { discardPending: boolean }): Promise<void>;
}
```

- **缓存隔离**：每个配置对应一个独立的 IndexedDB，库名为 `localmark:<cacheKey>`，其中 `cacheKey = sha256(mode + serverId/baseUrl + workspaceId)` 的前 16 位。切换服务器或 workspace 时，换的是整个缓存库，数据不会混在一起。
- **主机权限**：远程模式在添加服务器时调用 `chrome.permissions.request({ origins: [baseUrl + "/*"] })`。manifest 中改用 `optional_host_permissions`，不再写死某个域名。

### 4.2 LibraryRepository（UI 唯一入口）

现有的 `Request` 消息类型保持不变，background 内部改为调用 Repository。

```ts
interface LibraryRepository {
  /** 供 UI 渲染的视图，结构与现有的 Library 兼容，方便渐进迁移。 */
  snapshot(): Promise<LibraryView>;
  getPage(pageId: string): Promise<PageView | undefined>;
  findPageByUrl(url: string): Promise<PageView | undefined>;

  /** 每次写入都生成一条 op：写本地缓存、进入 outbox，然后通知 changed。 */
  apply(op: LocalOp): Promise<ApplyResult>;

  /** 冲突列表，以及用户的选择。 */
  conflicts(): Promise<Conflict[]>;
  resolve(conflictId: string, choice: "local" | "remote"): Promise<void>;

  subscribe(listener: (change: RepositoryChange) => void): () => void;
}

/** 视图层：把记录重新聚合成 UI 熟悉的形状（PageView 约等于现有的 Page）。 */
interface PageView {
  page: PageRecord;
  marks: MarkRecord[];          // 已过滤掉墓碑
  videoMarks: VideoMarkRecord[];
  syncState: "synced" | "pending" | "conflict" | "error";
  issue?: { kind: "conflict" | "invalid" | "io" | "auth" | "quota"; message: string };
}

type ApplyResult =
  | { ok: true; view: PageView | LibraryView }
  | { ok: false; reason: "stale"; message: string };  // 本机乐观校验失败（expectedXxx 不匹配）
```

### 4.3 本地操作（LocalOp）与 outbox

操作是幂等的，带 `opId`，重放不会重复生效。字段级的 `set` 便于自动合并互不相交的修改。

```ts
type LocalOp = {
  opId: string;                 // uuid，客户端生成，服务端据此去重
  at: string;                   // 客户端时间
} & (
  | { type: "upsert"; kind: RecordKind; id: string; baseVersion: number;
      /** 只包含本次修改的字段；新建时 baseVersion=0，并带上完整字段。 */
      set: Record<string, unknown>; unset?: string[] }
  | { type: "delete"; kind: RecordKind; id: string; baseVersion: number }
  /** 删除网页时级联删除它的 mark 和 videoMark，由服务端或适配器展开成墓碑。 */
  | { type: "deletePage"; id: string; baseVersion: number }
  /** 同一个分类或标签只保留一个：把 sourceId 合并进 targetId。 */
  | { type: "mergeTaxon"; sourceId: string; targetId: string; baseVersion: number }
);

interface Outbox {
  enqueue(op: LocalOp): Promise<void>;
  /** 取出待发送的一批操作，按入队顺序。 */
  peek(limit: number): Promise<LocalOp[]>;
  ack(opIds: string[]): Promise<void>;
  /** 发生冲突的 op 移入冲突区，不阻塞后续无关记录的上传。 */
  park(opId: string, conflict: Conflict): Promise<void>;
  size(): Promise<number>;
}
```

#### 现有 Request 到 LocalOp 的映射

| 现有消息 | 生成的 op |
|---|---|
| `save` | 页面不存在时，先生成 `upsert page`；再生成 `upsert mark` |
| `delete` | `delete mark` |
| `video-save` / `video-delete` | `upsert videoMark` / `delete videoMark` |
| `page-title` / `page-comment` / `page-rating` | `upsert page`，`set` 中只有对应字段 |
| `page-category` / `page-tag` | `upsert page`，修改 `categoryId` 或 `tagIds`；需要新建分类或标签时先生成 `upsert taxon` |
| `taxonomy` / `bulk-taxonomy` | 若干个 `upsert taxon`、`delete taxon`、`mergeTaxon` 和 `upsert page` |
| `page-delete` | `deletePage` |
| `resolve` / `resolve-taxonomy` | `LibraryRepository.resolve` |
| `highlight-palette` / `show-page-tools` / `auto-generate-markdown` | 设备设置，不进入 outbox |

### 4.4 LocalCache（IndexedDB 结构）

| object store | 主键 | 索引 | 说明 |
|---|---|---|---|
| `records` | `[kind, id]` | `pageId`, `updatedAt`, `url` | 最新的合并结果，包含本地尚未上传的修改 |
| `base` | `[kind, id]` | | 最近一次与远端一致的版本，用于三方合并和冲突展示 |
| `outbox` | `opId` | `seq` | 待上传的操作 |
| `conflicts` | `conflictId` | `[kind, id]` | |
| `media` | `sha256` | `uploaded` | 本地图片 Blob，以及是否已上传 |
| `meta` | key | | `cursor`、`profileId`、`schemaVersion`、`lastSyncAt` |

记录拆开存放后，每次写入只改动受影响的几条记录，不再整体重写整个 Library。

### 4.5 SyncAdapter

```ts
interface SyncAdapter {
  readonly kind: "none" | "localFolder" | "remote";
  readonly capabilities: {
    tombstones: boolean;        // 远端能否保存墓碑；本地文件夹只能借助缓存模拟
    media: boolean;
    multiUser: boolean;
    markdown: boolean;          // 能否生成 Markdown
  };

  /** 连接检查：权限、登录状态、协议版本。 */
  status(): Promise<AdapterStatus>;

  /** 拉取远端自 cursor 之后的变更；cursor 为 null 表示全量拉取。 */
  pull(cursor: string | null, limit: number): Promise<{
    changes: SyncRecord[];      // 包含墓碑
    cursor: string;
    hasMore: boolean;
  }>;

  /** 批量推送；同一批内的每条 op 独立给出结果，可以部分成功。 */
  push(ops: LocalOp[]): Promise<PushResult[]>;

  media: MediaStore;
}

type PushResult =
  | { opId: string; status: "applied"; record: SyncRecord }        // 服务端返回的权威记录（含新 version）
  | { opId: string; status: "duplicate"; record: SyncRecord }      // opId 已处理过
  | { opId: string; status: "conflict"; current: SyncRecord }      // baseVersion 落后
  | { opId: string; status: "rejected"; code: ErrorCode; message: string };

interface MediaStore {
  has(sha256: string): Promise<boolean>;
  put(blob: Blob, sha256: string): Promise<MediaRef>;
  get(ref: MediaRef): Promise<Blob | null>;
}

type AdapterStatus =
  | { state: "ready" }
  | { state: "needsPermission" }          // 本地文件夹需要重新授权，或服务器域名未授权
  | { state: "needsLogin" }
  | { state: "incompatible"; message: string }
  | { state: "offline"; retryAt: string };
```

#### 三种实现

- **`NoneAdapter`**：`pull` 总是返回空，`push` 直接全部返回 `applied`。由本地缓存给记录分配 `version`，每次加 1。
- **`LocalFolderAdapter`**：
  - 内部保留现有的 `SyncEngine`、`DirectoryFiles`、`metadata-names` 和冲突备份流程。
  - `pull` 用每个文件的内容哈希做游标，读回外部修改，再把聚合文档拆成记录。
  - `push` 把操作应用到聚合文档，然后按现有的比较后写入逻辑落盘。
  - 磁盘上无法保存墓碑。删除操作直接落盘，墓碑只保留在本地缓存的 `base` 中。
- **`RemoteAdapter`**：调用第 5 节的 HTTP API，令牌由 `AuthSession` 提供。

### 4.6 冲突（Conflict）与自动合并

```ts
interface Conflict {
  conflictId: string;
  kind: RecordKind;
  id: string;
  local: SyncRecord | null;     // null 表示本地已删除
  remote: SyncRecord | null;    // null 表示远端已删除
  base: SyncRecord | null;
  pendingOpIds: string[];
  detectedAt: string;
}
```

#### SyncCoordinator 的处理规则

1. 收到 `conflict` 后，先用 `base` 做字段级三方合并。如果本地修改和远端修改的字段没有交集，就自动生成一条新 op，`baseVersion` 取远端版本，然后重新推送。
2. 如果同一字段两边都改了，或者一边删除、一边修改，则进入 `conflicts`。UI 沿用现有的“保留本机 / 采用另一份”交互。被放弃的那份写入冲突备份：本地模式写到 `冲突备份/`，远程模式写到本地缓存的 `conflictArchive`。
3. `tagIds` 按集合合并：两边的新增都保留，两边的删除都执行。这样不会因为各自打了不同标签而产生冲突。

### 4.7 AuthSession

```ts
interface AuthSession {
  /** 打开服务端登录页面（chrome.identity.launchWebAuthFlow + PKCE），或者使用账号密码表单。 */
  login(server: ServerEndpoint): Promise<{ userId: string; displayName: string }>;
  logout(server: ServerEndpoint, options: { revoke: boolean }): Promise<void>;
  /** 返回有效的访问令牌；过期时自动用刷新令牌续期，失败则抛出 needsLogin。 */
  accessToken(server: ServerEndpoint): Promise<string>;
}
```

- 令牌只保存在 background 可访问的 `chrome.storage.local` 中，按 `serverId` 分开存放。content script 和网页都不会拿到令牌。
- 推荐使用 OAuth 授权码流程加 PKCE：登录页由服务端提供，插件不接触密码。

## 5. HTTP API v1

### 5.1 通用约定

- 基础路径为 `{baseUrl}/v1`，只使用 JSON 和 HTTPS。
- 认证头：`Authorization: Bearer <accessToken>`。
- 客户端标识头：`X-LocalMark-Client: <扩展版本号>`。服务端可以据此拒绝过旧的客户端。
- 时间一律使用 ISO 8601（UTC）。
- 错误响应格式：

```json
{ "error": { "code": "conflict", "message": "人类可读说明", "details": {} } }
```

- `ErrorCode` 的取值：`unauthenticated` | `forbidden` | `not_found` | `conflict` | `validation` | `payload_too_large` | `rate_limited` | `unsupported_client` | `internal`。

### 5.2 服务信息

```http
GET /v1/meta               # 不需要认证
```
```json
{ "serverId": "uuid", "name": "Meowa LocalMark", "apiVersion": "1.0",
  "minClientVersion": "0.4.0",
  "auth": { "type": "oauth2-pkce", "authorizeUrl": "...", "tokenUrl": "..." },
  "limits": { "maxOpsPerPush": 200, "maxRecordBytes": 2097152, "maxMediaBytes": 10485760 } }
```

### 5.3 认证与账号

```http
POST /v1/auth/token        # 授权码换令牌 / 刷新令牌（grant_type=authorization_code|refresh_token）
POST /v1/auth/revoke       # 注销当前会话的刷新令牌
GET  /v1/me                # 当前用户
GET  /v1/me/sessions       # 已登录设备列表
DELETE /v1/me/sessions/:id # 远程下线某台设备
```

关于令牌：

- 访问令牌有效期较短，建议 15 分钟。
- 刷新令牌每次使用后轮换，并且绑定设备名称，用户可以在 `sessions` 中逐台注销。

### 5.4 Workspace

```http
GET  /v1/workspaces
POST /v1/workspaces                      { "name": "...", "type": "team" }
GET  /v1/workspaces/:ws
GET  /v1/workspaces/:ws/members          # 首版只读；团队管理放到后续版本
```

```json
{ "id": "uuid", "name": "个人资料库", "type": "personal", "role": "owner",
  "createdAt": "..." }
```

- 角色分为 `owner`、`editor`、`commenter`、`viewer`。
- 首版只启用 `owner` 和 `editor` 的读写，以及 `viewer` 的只读。

### 5.5 同步

```http
GET /v1/workspaces/:ws/changes?cursor=<opaque|empty>&limit=500
```
```json
{ "changes": [ { "kind": "mark", "id": "…", "version": 42, "deleted": null, "...": "..." } ],
  "cursor": "opaque-string", "hasMore": false }
```

- 游标是不透明字符串，服务端可以用全局递增序号实现。
- 如果游标已经过期，比如墓碑已被清理，返回 `410 Gone`，客户端需要全量重新拉取。

```http
POST /v1/workspaces/:ws/ops
{ "ops": [ LocalOp, ... ] }              # 不超过 limits.maxOpsPerPush
```
```json
{ "results": [ PushResult, ... ], "cursor": "opaque-string" }
```

服务端在处理 ops 时需要做到：

- **按 `opId` 去重**：已经处理过的操作返回 `duplicate`。
- **逐条做乐观并发校验**：`baseVersion` 与当前版本不一致时，该条返回 `conflict`，同一批里的其他 op 照常处理。
- **校验数据**：沿用插件中的 zod schema，建议抽成一个前后端共享的包。
- **展开级联删除**：`deletePage` 会同时把该网页下的所有标注标记为删除（墓碑）。
- **整批原子性**：每条 op 在自己的事务中执行，不要求整批原子。

```http
GET /v1/workspaces/:ws/pages/lookup?url=<canonicalUrl>
```

这个接口用于打开网页时快速判断有没有该页的标注，避免像实验版那样每次都拉全量列表。返回 page 及其 marks 和 videoMarks，或者 404。

### 5.6 媒体

```http
HEAD /v1/workspaces/:ws/media/:sha256    # 已存在则返回 200，可跳过上传
PUT  /v1/workspaces/:ws/media/:sha256    # 请求体为图片；服务端校验哈希和 MIME
GET  /v1/workspaces/:ws/media/:sha256
```

### 5.7 服务端存储结构（参考）

```text
users(id, email, display_name, created_at)
sessions(id, user_id, device_name, refresh_hash, expires_at, revoked_at)
workspaces(id, name, type, created_at)
memberships(workspace_id, user_id, role)
records(workspace_id, kind, id, version, seq, data jsonb, created_at, updated_at,
        updated_by, deleted_at, deleted_by,  PRIMARY KEY(workspace_id, kind, id))
applied_ops(workspace_id, op_id, result jsonb, applied_at)   -- 幂等去重，按时间清理
media(workspace_id, sha256, mime, bytes, storage_key)
```

- `seq` 是 workspace 内全局递增的序号，`changes` 接口就按 `seq > cursor` 查询。
- 数据库用 Postgres 或 SQLite 都可以。媒体文件放 S3 兼容的对象存储，或者本地磁盘。存储层在服务端内部也做成接口，这样个人自建时用 SQLite 加磁盘即可。

## 6. 迁移

1. **插件现有数据**：首次启动新版本时，把 `kv/library` 拆成记录，写入以当前存储模式为配置的新缓存库。保留旧的 `kv` 库一个版本周期，作为回退手段。
2. **本地文件夹迁移到服务器**：在设置页提供“上传当前资料库到服务器 workspace”。流程是：先用 `pull` 读取全部本地记录，再生成 `upsert` 操作批量推送，图片按哈希去重上传。服务器上已经存在的同 ID 页面进入冲突处理，不直接覆盖。
3. **meowa-outline 实验目录**：用一次性的服务端导入脚本读取 `WEB_ANNOTATIONS_DIRECTORY` 中的 JSON，写入指定的团队 workspace。Outline 端此后改为通过 API v1 读取，作为可选的展示方。

## 7. 实施顺序建议

| 阶段 | 内容 | 用户可感知的变化 |
|---|---|---|
| 1 | `LocalCache` 按记录存储，加 `LibraryRepository`、`SyncAdapter`；`LocalFolderAdapter` 包装现有引擎；目录句柄访问全部收拢 | 无，功能保持不变，用现有测试回归 |
| 2 | 墓碑、outbox、字段级 op、冲突自动合并 | 本地多窗口和断续连接更稳定 |
| 3 | 服务端最小版本（meta、auth、个人 workspace、changes、ops、media、lookup），加插件端的 `RemoteAdapter` 和登录页 | 可以登录服务器并在多台设备间同步 |
| 4 | `ProfileRegistry` 多配置切换，`optional_host_permissions` | 可以切换服务器和 workspace |
| 5 | 团队 workspace、成员管理、分享和评论 | 协作 |

## 8. 待确认问题

1. **账号体系**：服务端自带账号（邮箱加密码），还是接入已有身份源（Outline、飞书、GitHub 等 OAuth）？这个决定影响第 5.3 节的具体实现。
2. **Markdown 生成**：服务器模式下是否还需要生成 Markdown？可选方案是由插件按需导出到本地文件夹，或者由服务端生成。
3. **双写**：是否需要同一个 workspace 同时同步到本地文件夹和服务器？首版建议不支持。
4. **团队库中的个人数据**：评分、页面评论这类数据，是否需要区分“个人”和“团队共享”？如果需要，`rating` 和 `comment` 要改成按用户存储的独立记录。
5. **部署形态**：服务端技术栈和部署方式。是沿用 meowa-outline 的 Node/Koa 和 Docker，还是做成独立的轻量服务？
