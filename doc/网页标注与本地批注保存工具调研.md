# 网页标注与本地批注保存工具调研

## 摘要

截至 2026 年 8 月 20 日，市面上已有不少“网页划线 + 批注”工具，但“每条划线都能附带批注，并持续自动写入用户指定的本地 Markdown 目录”仍是一个没有被成熟产品完整覆盖的交集。现成工具通常只满足其中两项：要么批注完整但数据留在浏览器数据库或云端，要么能写入本地 Markdown，却缺少逐条高亮批注的数据结构。

对于当前 Vault 工作流，最值得先试的是 **markClipper**；如果必须严格保存“原文摘录—个人批注”配对，并加入设备、目标位置和变更日志，**Marginalia 是更合适的二次开发底座**；如果接受云端中转，**Glasp + Obsidian 插件**的自动同步最完整。文中 `[cite:x]` 对应文末“来源”。

## 结论先行

### 最适合立即试用：markClipper

markClipper 是 Chrome 商店中的开源扩展，可以获得本地 Vault 的文件权限，把网页内容、选中文本和高亮直接写入指定的 Obsidian Markdown 文件；它不要求账号，也不需要额外安装 Obsidian 插件。商店版本还提供持久高亮、侧边栏笔记、选定目标笔记、用户自定义笔记目录，以及在侧边栏开启时将复制内容写入当前笔记的工作流。[cite:3][cite:4]

它和需求的主要差距是：现有说明能确认“高亮文本写入选定笔记”和“在侧边栏编辑笔记”，但没有证明每条高亮都有独立、结构化的批注字段。因此它更像“边看网页，边向本地笔记追加摘录并编辑”，而不是严格的“每条 quote 对应一个 comment”的批注数据库。建议先用一周验证这个差异是否影响实际使用。

### 最适合二次开发：Marginalia

Marginalia 的数据模型最接近目标：在 Firefox 网页中选中文本、为该文本写批注、按页面 URL 收集，然后输出到任意本地目录中的 Markdown。它现成的文件格式已包含来源、摘录、批注和时间；本地 FastAPI bridge 负责写文件。[cite:5]

它目前还不是成熟插件：仓库非常新，安装方式是 Firefox 临时扩展，浏览器重启后需要重新加载；写盘也要点击 Export，而不是每次批注后立即写入。另一方面，正因为代码量和边界清晰，它很适合补上当前工作流真正需要的字段：`device`、`browser_profile`、`target_path`、稳定 annotation ID，以及 append-only 的变更日志。

### 最省事的自动同步：Glasp + Obsidian 插件

Glasp 商店扩展支持网页、PDF 和 YouTube 的高亮，为具体高亮添加 note，并将数据同步到 Glasp 账号。[cite:8] 它的开源 Obsidian 插件可以把网页高亮与笔记写入用户指定的 Vault 文件夹，支持按小时、天或周后台同步，按 URL 增量更新已有 Markdown，而不是每次重复创建文件。[cite:9]

代价是数据先经过 Glasp 云端，并非本地优先。更重要的是，Glasp 官方说明当前免费方案默认公开高亮，私密高亮需要付费方案；因此不适合敏感网页、内部资料或私人批注，除非先确认账户的默认可见性。[cite:10]

### 最适合保留网页原貌：WebScrapBook

WebScrapBook 是维护活跃、同时上架 Chromium 和 Firefox 商店的开源网页归档扩展。它可以把页面保存到本地设备或自建后端，再对归档页面做高亮、带提示文本的标记和便签；保存格式包括文件夹、单 HTML、HTZ 或 MAFF。[cite:12]

它适合“网页以后可能失效，所以连页面和批注一起存档”的需求，但输出核心是可离线打开的网页档案，不是便于 Obsidian 检索和二次整理的 Markdown 摘录。因此它更适合作为证据归档层，而不是日常知识收集主入口。

## 评估口径

本次把“自动保存到本地”拆成四个不同等级，避免把“可以导出”误认为“会自动落盘”：

1. **直接本地文件**：一次授权后，操作结果直接进入指定 Markdown 或 HTML 目录。
2. **定时同步到本地**：先保存到服务端，再由 Obsidian 插件定时拉取到指定目录。
3. **浏览器本地数据库**：自动保存在 IndexedDB、`chrome.storage.local` 等浏览器内部空间，但不是用户可管理的普通文件。
4. **手动导出**：只有点击 Export 或 Download 后才生成 Markdown、JSON 或其他文件。

如果要求 Git 可追踪、普通编辑器可读、可被 Vault 内脚本继续处理，只有前两级真正等价于“落到本地某个位置”。第三级虽然不经过云端，但浏览器卸载、扩展重载或配置损坏时仍有丢失风险。

## 各方案的关键限制

### Obsidian Web Clipper：本地 Markdown 很强，但批注仍是缺口

官方 Web Clipper 开源、跨 Chrome、Edge、Firefox 和 Safari，剪藏结果会成为本地 Vault 中的持久 Markdown 文件。[cite:1] 但截至本次调研，“Annotate highlights”仍在路线图和实现提案阶段；现有流程主要是收集高亮后提交到 Obsidian，不是选中文本后立即附上一条个人批注。[cite:2]

因此，如果需求只是“保存若干网页高亮”，它是最稳妥的官方方案；如果“为什么标这段”与摘录本身同等重要，它目前不够用。

### Web Highlights：网页批注成熟，但本地文件仍靠导出

Web Highlights 支持网页和 PDF 高亮、给高亮写 note、标签、全文搜索、离线使用，以及导出 Markdown、HTML、PDF 或 Obsidian。基础使用无需登录，也可以只保存在本机浏览器中；跨设备同步和部分导出能力属于付费功能。[cite:11]

它很适合验证交互体验，但“离线”在这里表示数据位于浏览器扩展存储，并不表示每次批注都会写入指定的 Vault 文件夹。若最终仍要手工导出，它只能减少阅读时摩擦，不能完全打通收集链路。

### Web Annotations 与 Web Annotator：本地优先，但不是文件优先

Web Annotations 非常轻量，支持多色高亮、每条高亮的文字评论、重访页面时恢复，以及设置页导入导出；但数据保存在 `chrome.storage.local`，作者还明确提醒扩展更新或重载可能造成批注丢失，应提前导出。[cite:7]

Web Annotator 功能更完整：高亮可附 note，还有富文本便签、绘图、全文搜索，以及 Markdown、JSONL、W3C Web Annotation 导出；离线模式数据存入 IndexedDB，并提供本地 CLI、HTTP API 和外部集成接口。[cite:6] 它适合当作长期自研底座，但当前只有很少的仓库使用信号，没有商店安装包，不能按成熟成品对待。

### Hypothesis：标注层成熟，旧的 Obsidian 自动同步链已经失去维护

Hypothesis 本身是成熟的开源网页批注系统，但常用模式仍把批注写入 Hypothesis 服务。曾经的 Obsidian Hypothesis 社区插件能够启动时或按时间间隔同步、更新已有文章，也允许指定本地 highlights 文件夹；不过仓库已经明确归档并停止维护，还存在首轮和增量同步条数限制。[cite:13]

它仍可用于已有大量 Hypothesis 数据的迁移场景，但不建议在 2026 年把这个旧插件作为新的核心收集链路。

### Cubox：自动同步存在，但批注只是一次性快照

Cubox 浏览器扩展能直接在网页上高亮、改颜色并写 note，官方 Obsidian 插件也支持定时间隔同步和自定义目标文件夹。[cite:14] 关键限制是同步采用“单向、只创建不更新”：一个卡片第一次写入 Vault 后，之后在 Cubox 新增的高亮、批注或标签不会更新到已有 Markdown；官方把同步结果明确描述为当时的 annotation snapshot。

这意味着它更像“标完以后再归档一次”，不适合边读边同步。如果过早同步，后续批注可能永远留在 Cubox 云端，除非删除本地笔记再同步。

## 建议的落地顺序

### 第一阶段：用 markClipper 做低成本试验

在 Chromium 浏览器中安装 markClipper，只授权一个明确的中转目录，例如 `_中转/网页批注/`。用至少 20 个真实网页验证以下问题：

- 选中一段文字后，能否在两次操作内同时留下摘录和个人评价；
- 同一网页追加多次时，是更新同一个文件还是制造重复文件；
- 页面标题、源 URL 和时间能否稳定进入 Markdown；
- 网页 DOM 更新后，原网页高亮消失是否会影响本地材料的可用性；
- 侧边栏笔记能否形成稳定的“摘录—批注”配对，而不是混成一段连续文本。

若最后一项可以接受，就没有必要立即开发新工具。

### 第二阶段：若配对关系不可接受，改造 Marginalia

Marginalia 已经覆盖最难的主链路：网页选择、内联批注、按 URL 聚合、本地服务写 Markdown。二次开发只需要把“人工 Export”改成“保存批注后立即或延迟数秒写盘”，并补充可靠的数据字段和文件更新策略。

推荐每条批注至少保存：

```yaml
id: 稳定 UUID
source_url: 原网页地址
page_title: 网页标题
quoted_text: 被标注的原文
comment: 对原文的评语
created_at: 创建时间
updated_at: 修改时间
device: 设备名
browser_profile: 浏览器配置名
target_path: 最终写入位置
anchor: 用于回到网页位置的选择器信息
```

写盘策略应采用“一页一文件 + 一条 annotation 一个稳定 ID + append-only 事件日志”。这样既能在 Obsidian 中直接阅读，也能通过 Git 查看新增、修改和删除记录，并与现有对话日志体系对齐。

### 第三阶段：只有接受云端时才选 Glasp

如果实际使用证明“自动同步比完全本地更重要”，Glasp + Obsidian 插件是当前最完整的无开发方案。启用前应先完成两项检查：把默认可见性改为 Private，并确认对应付费方案；将 Obsidian 插件的 token 文件排除在 Git 和跨库分享之外。插件文档明确说明 token 保存在 Vault 的插件数据文件中，应按密码管理。[cite:9]

## 最终建议

当前没有一个同时满足“成熟商店安装、开源、逐条高亮批注、完全离线、无需手动导出、持续写入任意本地 Markdown 目录、带设备与变更日志”的现成工具。

最务实的路线是：

1. **先用 markClipper 验证工作流价值**，因为它最接近现有 Chrome + Obsidian + 本地 Markdown 环境，迁移成本最低。
2. **如果逐条批注关系确实是硬需求，基于 Marginalia 做一个小型专用版本**，不要从零写高亮锚定和页面注入。
3. **如果不想维护代码且可以接受云端，改用 Glasp + Obsidian 自动同步**，但必须先处理默认公开和 token 管理问题。
4. **重要网页另用 WebScrapBook 存档**，把“知识摘录”和“原页面证据保全”分成两层，不强求一个扩展同时解决。
