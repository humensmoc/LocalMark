# 网页批注工具进阶调研：本地文件回读、文本定位链接与悬停笔记

## 摘要

本次核查没有确认到同时满足全部要求、可直接推荐为成熟成品的工具。最接近“本地文件双向同步”的是 **lhh-pi/web-notes**，最接近“逐页文件导出与原文悬停评论”的是 **shyenx/web-highlighter**，而 **salcc/Web-Annotations** 能实现手动 JSON 导入后恢复高亮和悬停评论。三个项目各自缺少另一部分，不能拼成一个已经存在的完整产品。

如果优先使用成熟浏览器商店工具，可考虑 Web Highlights；如果优先让摘录进入 Obsidian Markdown，可考虑官方 Web Clipper 或 markClipper。但“可导出到本地”“重访原网页能高亮”不等于“浏览器重新读取本地笔记来高亮”。社区确实存在后一种需求，而且用户反复提到重复追加、跨设备不同步、无法在原文直接看到评论和数据锁定。正文引用对应文末来源。

## 1. 本次到底在检查什么

将需求拆为六项，避免笼统的“支持批注”掩盖差异：

| 编号 | 能力 | 判定条件 |
| --- | --- | --- |
| A | 选中文本并写评论 | 每条引文能关联自己的评论，而不是只有整个网页的一段笔记 |
| B | 同页一个本地文件 | 普通文件系统中能找到文件；同一 URL 的多条摘录聚在一起，继续摘录能更新同一文件 |
| C | 来源与文本定位链接 | 除原网页 URL，还能回到那段文字并高亮；优先考察原生 Text Fragment |
| D | 从本地文件恢复网页高亮 | 读入或同步文件中的数据后，在原始线上网页重新渲染；不能只是看浏览器旧缓存 |
| E | hover 显示笔记 | 鼠标停在原文高亮处即可看到评论正文；点击弹窗、侧栏卡片、导览点悬停分别记录 |
| F | Chrome / Edge 可用 | 文档明确支持，或仅为 Chromium 技术上可尝试；本轮未安装验收 |

“本地”至少存在四种不同机制：浏览器内部数据库、手动下载备份、持续读写普通文件、云端数据同步到普通文件。用户这次的目标尤其依赖后两者中的双向能力。文件也不一定必须是 Markdown：JSON/JSONL 更容易完整保存批注关系，但对 Obsidian 阅读和人工维护不如 Markdown 直观。

## 3. 最值得关注的三个小型项目

### 3.1 Web Notes：真正读写本地文件，但所有网页共用 JSON

准确项目为 **lhh-pi/web-notes**，MIT，README 明确支持 Chrome / Edge 122 及以上。用户选中文本后可通过右键高亮并添加笔记；评论支持 Markdown 编辑和预览。数据先进入 IndexedDB，可选择一个真实的本地 JSON 文件进行双向同步，不需要额外 Python 服务。云盘目录只是可选的跨设备传输方式，本机使用不要求接入云服务。[cite:2]

这里确认到了真正的文件回流链：读取文件、合并文件记录与浏览器数据、导出合并结果、写回文件。源码中的 `READ_FILE → mergeFromText → exportToJSON → WRITE_FILE` 表明它不是单纯下载备份。自动模式采用防抖写入和周期性检查外部文件，手动模式也可触发同步。[cite:3]

与需求的差距：

- 所有网页集中到一个 `web-notes.json`，不是每网页一个 Markdown 或 JSON。
- “支持 Markdown”指评论编辑内容，不代表输出 Markdown 文件。
- 评论是点击高亮后打开气泡。源码的提示文字为 `Click to view/edit note`，绑定点击事件；不能把气泡界面算成 hover 评论。[cite:4]
- 本轮没有发现原生 Text Fragment 分享链接生成。
- 外部编辑 JSON 需要遵循其结构、更新时间和删除标记机制；它不是任意文本文件监听器。双向合并也不意味着并发编辑永无冲突。

维护方面，README 明确表述项目由 AI 辅助构建，作者不保证修复所有 issue，更鼓励使用者自己修改。因此建议把它视为值得试验和二次开发的项目，而非已获大量长期用户验证的成熟替代品。[cite:2]

**判断：如果“文件能反向驱动网页批注”优先级最高，这是本轮最值得先试的候选。**

### 3.2 Web Highlighter：原文 hover 和单页导出明确，缺少文件读回

准确项目为 **shyenx/web-highlighter**，MIT，README 明确面向 Chrome，需加载未打包扩展；Edge 本轮未测试。它支持多种划线样式、逐条笔记、重访恢复和当前页 JSON 导出，不要求账号。[cite:5]

hover 有直接代码证据：高亮 DOM 元素使用 `el.title = note`。鼠标停留会显示笔记正文，但这是浏览器原生提示框，不是可交互的 Markdown 富文本卡片。[cite:6]

导出的 JSON 包含当前页 URL 和所有 marks，因此可以把同一页摘录放进一个文件。不过文件名主要根据域名生成，同站不同文章可能有相同建议文件名；下载管理器处理重名，不等于工具按 URL 自动维护唯一档案。[cite:7]

本轮没有找到 JSON 导入入口。网页恢复的数据来自 `chrome.storage.local`，不是已经导出的文件。Markdown 导出仍列在路线图里。[cite:5]

**判断：如果可以接受手动保存，而当前最想体验“原文高亮＋鼠标悬停评论”，它比泛用剪藏器更贴近目标。**

### 3.3 Web Annotations：手动导入 JSON 后恢复高亮与评论

准确项目为 **salcc/Web-Annotations**，文档明确 Chrome、Edge 等 Chromium 浏览器可用。它支持选区高亮、逐条 comment、原文 hover 显示评论，并有 JSON 导入导出。[cite:8]

源码显示，导出结构的 `annotationsByUrl` 以页面 URL 为键，记录文本、comment、位置和前后文；导入时从文件读取，选择合并或替换，再写入 `chrome.storage.local`。页面脚本据此恢复高亮。[cite:9]

它满足较宽松的 D：“拿一个本地备份文件，导入后把网页恢复出来”。但它不持续监控本地文件，也不默认每网页输出一个独立文件。来源链接目前只确认普通 URL，未确认文本片段深链。

维护边界也需分清：本轮未在仓库根目录确认明确许可证，应称**源码公开、许可未明确**，不能直接当成 MIT/GPL 项目推荐二次发布。README 提醒开发者模式安装没有自动更新，更新或重载前应导出备份；这项提醒来自项目自身，未在本轮复现数据丢失。[cite:8]

**判断：它适合验证完整的“备份→导入→网页高亮→hover 评论”交互，但离持续维护的一页一文件工作流仍有距离。**

## 4. 更成熟的工具，以及它们为什么仍有缺口

### 4.1 Obsidian Web Clipper：不要把 JSON 导入与 Vault 回读混为一谈

官方扩展 MIT，明确提供 Chrome 和 Edge 安装入口；可将剪藏保存为本地 Markdown。模板可以选择追加已有笔记，因此能组织为同页一篇笔记，但模板追加不等于以批注 ID 做增量更新。[cite:10][cite:34]

网页高亮加载函数明确从 `browser.storage.local` 读数据。另一个主线源码文件确实已经有 `importHighlightsFromJson`：它读取 JSON，按页合并后写回浏览器库。[cite:11][cite:12]

因此不能简单写“Obsidian Clipper 完全无法从文件恢复”。准确说法是：**主线具备高亮 JSON 导入逻辑，但没有据此证明它读取 Vault Markdown 或持续双向同步。** 本轮也未核验这份 main 分支源码与当前各浏览器商店版本是否完全一致。

关于评论，README 仍将 Annotate highlights 列为待办，相关实施提案仍开放。与此同时，源码已经有 `notes` 字段、导出/导入和列表展示的相关处理。数据模型能携带 notes，不等于用户已经可以在原网页选择文本、立即写评论并 hover 查看；本轮查到的主要高亮调用入口也没有传入评论内容。[cite:10][cite:11][cite:12][cite:33]

**适合：本地 Markdown 和官方维护优先；不适合把它当成现成的 Vault 双向网页批注系统。**

### 4.2 markClipper：直接写 Markdown 是优势，批注恢复机制仍不清楚

项目 **anilkumarum/mark-clipper** 为 GPL-3.0。README 明确支持任意本地文件夹、选择现有笔记、高亮写入笔记以及重访网页时显示高亮，具备直接文件权限工作流。[cite:13]

源码核查能看到目录句柄与真实 `.md` 文件读写链，但高亮实现的部分被引用路径在公开树中缺失，无法据此确认是否从 Markdown 重建高亮。社区还有用户询问商店 0.0.7 版本源码在哪里。这只能说明发布版本与源码对应关系需要进一步核验，不能推断商店版本一定有问题。[cite:13][cite:32]

**适合：浏览网页时向指定本地笔记追加材料；不能把“持久高亮”直接解释为“从本地笔记重建高亮”。**

### 4.3 Web Highlights：常用功能完整，Obsidian 仍是手动复制

官方文档明确每条高亮可附富文本评论，支持原文点击后编辑，重新加载网页时恢复高亮。它还有页面边缘的导览轨道：悬停一个圆点即可查看对应的引文、笔记和标签。[cite:14][cite:15]

这里要区分两个位置：**悬停的是边缘导览点；本轮未确认直接悬停原文高亮处会自动弹出同样的笔记卡片。** 如果用户接受这个交互，它已能解决“在原页面快速查看评论”的大部分体验问题。

当前 Markdown 文档非常明确：没有直接 Obsidian API 集成，流程为 Copy Markdown，再粘贴进 Obsidian。复制内容包括引文、评论、标签、页面标题与 URL；当前文档标注该功能适用于所有方案，不应沿用旧文章笼统说 Markdown 导出必须付费。[cite:16]

本轮没有确认 Markdown 文件导回网页或持续读取本地目录。它应作为成熟交互工具评估，而不是文件双向系统。

### 4.4 Glasp＋Obsidian：自动入库，不是本地笔记反向同步

官方 Obsidian 插件可按小时、天或周同步，将网页高亮与笔记写入指定文件夹，按来源 URL 匹配并更新已有笔记。该插件采用 MIT；这不意味着整个 Glasp 浏览器扩展及云服务都是开源的。[cite:17]

同一 README 明确说插件只有只读访问权限，不把本地笔记发送出去。因此，在 Obsidian 修改评论，不会据此同步改变原网页上的 Glasp 评论。它覆盖“云端批注→本地 Markdown”，没有覆盖反向链。[cite:17]

**适合：愿意把云端作为批注主数据源，希望定时进入 Vault 的用户。** 本轮未重新确认 Glasp 当前私密方案和价格，不把旧笔记中的价格/可见性规则当作最新事实。

### 4.5 WebScrapBook：如果保留原页面比实时覆盖更重要

WebScrapBook 支持把网页保存成文件夹、HTZ/MAFF 或单 HTML，并在捕获前后高亮、批注、编辑。独立文件模式可以每页保存一份网页档案。[cite:18][cite:19]

维护者说明工具支持高亮上的 tooltip annotation。这里最明确的对象是保存后的网页副本：打开本地副本看原文及批注，不等于浏览器访问线上原始 URL 时从本地摘录文件自动覆盖。[cite:20]

当前说明还包含 re-capture：重新捕获时尝试将旧批注迁移到新版本；两版变化较大仍可能失败。不能拿很早的 issue 断言今天没有这个功能。[cite:19]

**适合：网页可能被删除、需要保留证据原貌；不适合直接替代可人工维护的 Markdown 摘录库。**

## 5. 其他开源底座与排除项

### Web Annotator：完整恢复用 JSONL，不要只看 Markdown 导出

**codyhxyz/web-annotator** 采用 ISC，具备高亮、关联便笺、IndexedDB 本地模式、Markdown/JSONL/W3C Annotation 导出，以及可选云端功能。README 将 JSONL 明确定位为可以完整往返的数据格式；CLI 的 SQLite 库则明确独立于浏览器扩展，不能据此推断两者已经本地双向同步。[cite:21]

Markdown 导出源码的注释写着“one file per URL”，但实际全库导出把多页文档拼接后一次下载；限定 URL 才是单页输出。高亮与 Notes 还分开呈现，未在 Markdown 中保留便笺的 `linkedHighlightId`。因此“人能读懂的导出”与“机器能完整恢复对应关系”应分别评价。[cite:22]

它适合作为二次开发底座，尤其适合明确要保留标准化锚点和完整数据关系的情况。本轮没有证实原文 hover 评论。

### Hypothesis：批注系统成熟，但常规数据源仍是服务端

Hypothesis 客户端使用 BSD-2-Clause，是网页批注服务的客户端，可用于浏览器扩展或嵌入网页。它适合讨论成熟批注系统、共享与标准数据模型，但不能因为开源就直接判定“默认每页一个本地文件”。[cite:23]

另外，本地 Markdown 与网页双向同步需要独立集成，不能把某个导出插件的存在当作原生支持。关于网页改版和异步内容导致批注失配，后面的社区证据也显示它不是一个任何网站都不会失败的问题。[cite:30]

### 不宜优先推荐的候选

本轮还检查了几种同名 Marginalia、NoteStash 和其他剪藏项目。没有将它们放进主推荐，原因包括只支持 Firefox、按页再导出覆盖旧文件、刷新后高亮不保留、README 的 hover 宣称未得到代码支持等。产品名称容易重名，安装或继续调研时必须用完整 GitHub 作者/仓库标识。本段属于候选筛选记录，不以这些项目未核验的功能作推荐依据。

## 6. Text Fragment 与永久批注，是两层不同能力

原生 `#:~:text=` 的职责是打开网页时查找文本、滚动并高亮。它可以包含文本开头/结尾及用于消歧的前后文，也可在同一个 URL 指定多段文本。原文改变、找不到匹配或正文位于不受支持的上下文时，定位可能失败。[cite:1]

它本身不保存“你为什么高亮”、评论内容、颜色、批注 ID，也不会扫描本地文件并把全部历史批注重建出来。即使给每条摘录生成 Text Fragment 链接，仍然需要扩展完成 D 和 E。

所以，可以将完整目标拆成两层：

1. **分享与回跳层**：每条引文附原生 Text Fragment 链接；别人不安装同一扩展，也有机会跳到对应文字。
2. **个人批注层**：扩展读本地记录，按 URL 和锚点找回所有高亮，再在 hover 时显示评论。

本次核心候选里，自动生成原生文本片段深链普遍没有得到证实。对这项需求最稳妥的表述是“需要额外手动复制 Chrome/Edge 的高亮链接，或补充生成逻辑”，而不是假定工具所有来源链接已经支持。

若后续需要开发，建议批注文件保留稳定 ID、原 URL、规范化 URL、quote、comment、时间和锚点。W3C TextQuoteSelector 的 `exact/prefix/suffix` 就是保存原文及上下文、区分重复文本的标准表达；仅保留一条普通链接不足以可靠恢复。[cite:24]

这也是为什么“一个人可读的 Markdown 文件”要成为双向数据源，通常仍需嵌入结构化字段，而不能只依靠任意排版的引用段落。这里是实现建议，不是声称某个候选已经完成。

## 7. 社区真正提出了哪些需求

### 对优缺点的评价并非单一方向

**被重视的优点**：在原文直接批注、自动进入自己的知识库、导出格式易用、重访能恢复上下文。Readwise 用户的“体验很好但贵”正说明便利性本身有价值。[cite:29][cite:31]

**被反复指出的摩擦**：同一批摘录重复追加、评论必须切换到别处再写、浏览器与 Vault 各自保存导致两份状态、本地导出需要反复操作。[cite:25][cite:27][cite:29]

**权限偏好存在分歧**：Obsidian #112 中，有用户愿意主动选择开启本地读取，也有用户不愿让网页相关扩展访问本地内容。维护者的移动端/权限考虑也真实存在。因此更合理的产品设计是明确授权范围和可选模式，不能说“大家一致要求双向”或“大家一致反对本地读取”。[cite:26]

**可靠性是独立维度**：文件已经保存，不代表原网页的 DOM 和文本永远不变；文字仍存在，也可能因为异步加载而暂时失配。应保留未定位的引文与评论，提供重新绑定，而不是删除记录。[cite:2][cite:30]

## 8. 针对当前工作流的建议

### 如果想先选一个尝试

- **文件回流第一优先：Web Notes（lhh-pi）**。接受全库 JSON 和点击评论，先验证读写链是否稳定。
- **原文 hover 第一优先：Web Highlighter（shyenx）**。接受手动单页导出，以及暂时没有文件导回。
- **导入备份后恢复＋hover 第一优先：Web Annotations（salcc）**。接受全库 JSON、手动导入和许可尚不明确的边界。
- **浏览器商店成熟交互第一优先：Web Highlights**。接受边缘导览点 hover 与手动复制 Markdown。
- **Obsidian Markdown 第一优先：官方 Web Clipper / markClipper**。接受暂未证实从 Vault 文件反向恢复完整批注。

这里推荐的是试用顺序，而不是宣布某款全部满足。浏览器可读取自己授权的文件，在技术上已经有实现证据；当前缺的是把逐页文件、完整批注关系、文本深链、hover 和稳健同步同时整合成可长期依赖的成品。

### 如果所有条件都是硬需求

更接近目标的开发起点是 Web Notes 的文件同步链，而不是从只会单向剪藏的工具起步。可评估补充三项：按规范化 URL 分文件、原文 hover 展示评论、生成 Text Fragment 链接。

但不能把它估成只加三个按钮：分文件会改变索引、权限、冲突合并和删除同步；如果文件改为 Markdown，还需定义可靠的批注 ID 与结构化字段。也可以采用“每页一个结构化文件＋可读 Markdown 视图”，不过这会增加文件数量，需由实际使用偏好决定。

### 最小验收清单

在少量真实文章上完成以下检查，就比只看宣传页更能判断适用性：

1. 同页创建三条摘录，每条独立评论；关闭重开后检查。
2. 在新浏览器配置中仅通过本地文件导入/同步，确认能恢复，排除旧缓存造成的假成功。
3. 修改文件中的一条评论并按格式更新时间，检查网页是否更新；再从网页修改，检查是否回写同一记录。
4. 重复同步，确认不重复、删除不复活、不覆盖已有人工说明。
5. 对同一句话出现两次、异步加载和 SPA 导航页面，检查锚点与未定位提示。
6. 关闭扩展后打开分享链接，确认 Text Fragment 能独立定位；打开扩展再确认 hover 评论来自批注数据。

以上是建议验收步骤，本轮没有实际安装扩展执行。
